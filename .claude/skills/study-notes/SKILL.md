# study-notes — 학습 정리 문서 작성

`Docs/Study/`는 나중에 복기할 때 프로젝트를 이해하기 위한 문서다. **"왜 이렇게 만들었는지"**를 남기는 것이 목표다. 코드 전문은 저장소에 있으므로 문서에는 핵심 코드와 이유만 담는다.
이 문서가 원본이다. Notion(`notion-sync` 스킬)은 사본이다.

## 1. 언제 쓰나

| 시점 | 할 일 |
|---|---|
| Step 하나 끝남 (사용자 완료 알림 → 리뷰 끝) | 해당 Phase 파일에 Step 섹션 추가, Step 표 상태 갱신. **Plan.md "📍 현재 진행 상황"도 함께 갱신** (같은 시점에 한다) |
| 확인 질문에 답이 옴 / 해설 요청 | 해당 Step의 🧩 복습 질문 갱신 |
| 새 Phase 시작 | 새 파일 `Phase<번호>_<영문 주제>.md` + README 목차 행 갱신 |
| Phase 끝남 | README 목차 상태 ✅, 🧭 전체 그림 갱신 → 그다음 Notion 업로드 여부를 사용자에게 묻는다 (`notion-sync`) |

쓰기 전에 **대화에서 아래 재료를 모은다.** 파일에는 없고 대화에만 있는 것이 대부분이다.
- 사용자가 실제로 쓴 코드 (파일을 직접 읽는다. 리뷰 후 고친 최종본 기준)
- 리뷰에서 지적한 점, 빌드 오류, 사용자가 막혔던 지점 → ⚠️ 겪은 실수
- 설계를 그렇게 정한 이유, 설명에 쓴 비유 → 📖 개념 / 🧱 핵심 코드 설명
- 확인 질문 원문과 사용자 답변 원문
- 사용자의 MEMO 주석 내용
- 누가 작성했는지 (사용자 / 요청으로 Claude가 작성)

## 2. 파일 규칙

| 항목 | 규칙 |
|---|---|
| 위치 | `Docs/Study/README.md` (목차, 전체 그림, 공통 규칙) + Phase별 파일 (`Phase1-2_Synchronization.md` 형식) |
| 인코딩 | UTF-8 (기존 파일의 BOM 유무와 줄바꿈을 그대로 유지한다. 새 파일은 기존 Phase 파일과 같게) |
| 허용 문법 | 제목, 표, 코드 블록, `>` 인용, `---` 구분선만. **HTML 태그, 토글 금지** (Notion 가져오기 호환) |
| 콜아웃 | `>` 인용 맨 앞 이모지로 구분: 💡 핵심/팁, 📝 내 메모·기록, ⚠️ 주의·함정, 🔧 개선 메모, 🧩 연결/복습, 🗺️ 다이어그램 링크 |
| 코드 블록 | 언어를 붙인다 (`cpp`, `bash`). 그림/트리는 언어 없이 |

## 3. Phase 파일 구성

```
# <이모지> Phase X-Y. <주제>

> 💡 **목표**: <Phase 전체 목표 한두 줄>

> 🗺️ 인터랙티브 다이어그램: Docs/Diagrams/<파일>.html — <볼 수 있는 것>   (있을 때만)

| Step | 파일 | 한 줄 요약 | 상태 |      ← Step마다 행 추가, 상태 ✅ / ⬜

---

## Step N. <이름>
### 🎯 목표
### 📖 개념          (여러 개면 "📖 개념 1 — <소제목>")
### 🧱 핵심 코드
### ⚠️ 겪은 실수
### 🧪 테스트 (`GameServer/Test.cpp`)   (테스트가 있을 때)
### 🧩 복습 질문

---
```

### 섹션별 작성 규칙
- **🎯 목표**: 한두 줄.
- **📖 개념**: 왜 필요한지 → 어떻게 동작하는지. 대화에서 쓴 비유가 있으면 `> 💡 **비유**:`로 넣는다. **설계 선택의 이유도 여기나 🧱에 녹여 쓴다.**
- **🧱 핵심 코드**: **사용자의 실제 코드 기준**으로 발췌한다 (전문 X). 코드 아래에 왜 이렇게 했는지 짧게 쓴다.
- **⚠️ 겪은 실수**: 실제로 겪은 것만 쓴다 (빌드 오류 메시지, 리뷰 지적, 잘못 이해했던 개념). 지어내지 않는다. 없으면 섹션을 생략한다.
- **🧪 테스트**: 표 `| 함수 | 확인 | 기대 결과 |`. 크래시 테스트는 확인 방법(F5)과 확인 날짜를 📝로 적는다. 누가 작성했는지 📝로 남긴다.
- **🧩 복습 질문**: 아래 4절.

## 4. 복습 질문 기록 형식

```
**Q1. <질문 원문>**
> ✅ <사용자 답 요약>            ← 맞음
> ❌ 내 답: <사용자 답>           ← 틀림
> 🔺 내 답: <사용자 답>           ← 일부 맞음
> 💬 보충: <Claude의 보충 설명>
> 💬 (해설 요청) <해설>           ← 사용자가 답 대신 해설을 요청함
(미답변)                         ← 아직 답이 없음
```
- **미답변 질문의 답을 Claude가 미리 채우지 않는다.** `(미답변)`으로 남긴다. 해설은 사용자가 요청했을 때만 `💬 (해설 요청)`으로 쓴다.
- 사용자 답은 뜻을 바꾸지 않는다. 틀린 답도 그대로 남기고 보충으로 바로잡는다.

## 5. 금지

- **"🔧 강의와 다른 점" 섹션을 쓰지 않는다** (2026-11-11 사용자 요청. 이전에 쓴 섹션은 유지). 강의와의 비교는 대화에서만 한다. 문서 본문에 "강의에서는", "강의 대신" 같은 비교 문구도 넣지 않는다.
- 강의 코드(`MMOServer_example/`) 원문을 넣지 않는다.
- 코드의 MEMO 주석은 건드리지 않는다. 내용을 문서로 옮길 때는 `> 📝 내 메모:`로 **원문 그대로** 인용한다.
- 크기·정렬·오프셋 값은 테스트 출력이나 `STATIC_ASSERT`로 확인된 값만 쓴다.

## 6. README 갱신

- 🗂️ 목차 표: Phase 행의 문서 링크, 주제, 상태 (⬜ → 🟡 진행 중 → ✅ 완료)
- 🧭 전체 그림: Phase가 끝날 때 include 구조, 전역 객체, 호출 경로 그림을 현재 코드에 맞춘다.
- 🏷️ 공통 규칙 요약: CLAUDE.md에 새 규칙이 생기면 반영한다.

## 7. 마무리

1. 다이어그램이 이해에 필요한 Step이면 `study-diagram` 스킬로 만들고, 문서에 🗺️ 링크 한 줄을 넣는다.
2. 고친 파일을 Plan.md와 함께 사용자에게 한 줄로 알린다 (어느 파일의 어느 Step).
3. 커밋은 사용자가 요청할 때만 한다 (`docs: ...`).
