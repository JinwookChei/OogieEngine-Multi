Debug의 모든 할당은 여기로 온다. 크기를 바꿔 보면 alignedSize, totalSize, offset이 Allocator.cpp와 같은 식으로 계산되고, 페이지 안에서 데이터가 어디에 놓이는지 보인다.

앞쪽 빈 공간 (offset, 커밋됨) 사용자 데이터 올림 여분 (넘쳐도 못 잡음) 커밋 안 된 주소 → 접근하면 AV

5. MemoryPool 하나를 직접 조작해 보기 (128 풀)

버튼으로 Pop과 Push를 해 본다. 빌려준 블록을 누르면 그 블록이 Push된다. SLIST_HEADER는 빈 블록 스택의 꼭대기를 가리키고, Push와 Pop은 모두 꼭대기에서 일어난다 (LIFO).

풀 안 (allocSize_ = 0) 빌려준 블록 (allocSize_ = 블록 크기) 방금 움직인 블록
풀 안 (header_부터 Next를 따라감)
밖에 빌려준 블록 (눌러서 Push)

header_는 꼭대기 주소와 순번을 16바이트 하나로 묶어 원자적으로 비교교환한다. 순번이 ABA 문제를 막고, 그래서 여러 스레드가 락 없이 동시에 Push/Pop 할 수 있다. 방금 돌려받은 블록이 다음 Pop에서 바로 나가므로 CPU 캐시에 남아 있을 가능성이 높다.

6. Allocate와 Release 순서

Memory::Allocate(size)

  1. size 범위 검사 (0 이하, Int32 넘침 → 크래시)
  2. blockSize = size + 16
  3. 4096 이하 → poolTable_[blockSize]->Pop()
    초과 → _aligned_malloc(blockSize, 16)
  4. AttachHeader: 헤더 생성, allocSize_ = blockSize
  5. header + 1 반환 (16 정렬)

Memory::Release(ptr)

  1. nullptr이면 크래시 (ASSERT_CRASH). xdelete(nullptr)은 그 전에 PoolAllocator::Release가 걸러 낸다
  2. DetachHeader: ptr − 16 = 헤더
  3. blockSize = allocSize_ (0이면 이중 해제 → 크래시)
  4. 4096 이하 → poolTable_[blockSize]->Push() (allocSize_ = 0)
    초과 → _aligned_free

7. Vector와 StlAllocator: 재할당마다 풀이 바뀐다

Vector<Int32>는 std::vector<Int32, StlAllocator<Int32>>다. 공간이 모자라면 vector가 allocate(새 용량)으로 더 큰 블록을 받고, 원소를 옮긴 뒤 옛 블록을 deallocate한다. push_back을 눌러 Release 빌드에서 어느 풀을 오가는지 본다.

push_back용량allocate(새 용량)deallocate(옛 블록)

새 용량은 MSVC STL 규칙(옛 용량 + 옛 용량/2, 모자라면 필요한 만큼)으로 계산했다. 바이트 수 = 용량 × sizeof(Int32)(4). 용량이 1066이 되는 순간 블록이 4096을 넘어 풀을 거치지 않는다. 미리 reserve하면 이 재할당이 한 번으로 줄어든다. Debug 빌드는 같은 호출이 모두 StompAllocator로 가고, MSVC가 반복자 검사용 작은 객체를 따로 하나 더 할당한다.

8. ObjectPool: 타입 하나에 전용 풀 하나

ObjectPool<Type>은 GMemory의 공용 풀을 쓰지 않는다. 타입마다 함수 안 static ObjectPoolBase SBase가 하나씩 생기고, 그 안에 블록 크기가 sizeof(Type) + 16으로 딱 맞는 MemoryPool을 하나 갖는다.

GMemory (xnew, MakeShared, STL)ObjectPool<Type>
풀 개수48개를 모든 타입이 같이 쓴다타입마다 1개 (ObjectPool<Knight>, ObjectPool<Monster>는 다른 SBase)
블록 크기32/128/256 간격으로 올림 → 남는 칸 생김sizeof(Type) + 16 그대로 → 남는 칸 없음
풀 찾기poolTable_[blockSize] 조회조회 없음. 컴파일 시점에 타입으로 정해짐
사용량 보기크기별로 섞여서 타입별로 셀 수 없음GetUseCount() = 이 타입 객체가 지금 몇 개 밖에 있나 (Release만)
헤더 포함 이유Release가 크기를 몰라서 allocSize_로 풀을 찾음풀은 이미 알지만 SLIST 노드 자리와 이중 해제 검사(allocSize_ = 0)가 필요
Debug둘 다 StompAllocator로 간다. ObjectPool은 #ifdef _DEBUG로 Pop/Push 안에서 직접 분기한다

MemoryPool은 Windows.h가 필요한 내부 전용 타입이다. 그래서 템플릿 ObjectPool<Type>(헤더에 전부 있음)은 MemoryPool을 모르고, 템플릿이 아닌 ObjectPoolBase가 MemoryPool*을 들고 .cpp에서만 다룬다.

9. 두 MakeShared: 객체와 컨트롤 블록은 어디로 돌아가나

shared_ptr는 객체 말고도 참조 카운트를 담은 컨트롤 블록이 필요하다. 두 MakeShared는 이 두 덩어리를 받는 곳과 돌려주는 시점이 다르다. Release 빌드 기준이다 (Debug는 모든 블록이 StompAllocator로 간다).

⚠️ 이 섹션은 아직 답하지 않은 확인 질문의 답을 그대로 보여 준다: Step 6-2 Q1(weak_ptr만 남았을 때 메모리 반납 시점), Step 8-2 Q1(남은 것과 돌아간 것), Step 8-2 Q2(할당기 인자를 뺀 2인자 버전). 먼저 답해 보고 확인용으로 여는 것을 권한다.

방식
컨트롤 블록 (strong/weak 카운트) 사용 중 풀에 돌아가 재사용 대기 OS 힙에 반환
